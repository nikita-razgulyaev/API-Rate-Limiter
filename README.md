# RateShield — открытое демо rate limiter'а

Небольшой открытый проект для демонстрации инженерного подхода: защита API от
перегрузок тремя проверенными алгоритмами лимитирования, живой дашборд
использования и архитектура, которая работает без единой внешней зависимости
и превращается в распределённый прод-грейд лимитер добавлением одной
переменной окружения. Никакого биллинга, аккаунтов или тарифов — просто демо.

## Зачем это нужно

Любой публичный API рано или поздно упирается в один и тот же вопрос: *что
делать, когда один клиент присылает запросов больше, чем система может
обработать?* Без rate limiting — это упавший прод для всех остальных клиентов
одновременно. Проект показывает, как решить это на практике:

1. **Защита инфраструктуры** — лимиты применяются до того, как запрос дойдёт
   до дорогой бизнес-логики или внешнего платного API.
2. **Прозрачность для интеграторов** — заголовки `X-RateLimit-*` в каждом
   ответе показывают остаток квоты и время сброса, не заставляя гадать вслепую.
3. **Наблюдаемость** — живой дашборд агрегирует использование в реальном
   времени, показывая, какой алгоритм и как часто блокирует запросы.

## Быстрый старт

```bash
npm install
cp .env.example .env   # можно оставить REDIS_URL пустым
npm start
```

Открой `http://localhost:3000` — там лендинг, плейграунд и дашборд.
Без Redis сервер сам переключается в in-memory demo-режим: ничего
дополнительно настраивать не нужно, чтобы посмотреть демо.

Для распределённого лимитинга (несколько инстансов сервера за балансировщиком)
задай `REDIS_URL` в `.env` — код лимитеров не меняется, меняется только
storage-бэкенд. Или подними всё сразу вместе с Redis:

```bash
docker compose up --build
```

## Алгоритмы

| Алгоритм | Как работает | Компромисс |
|---|---|---|
| **Fixed Window** | счётчик на временное окно | дёшево, но допускает 2x всплеск на границе окон |
| **Sliding Window** | скользящий журнал таймстампов (Redis sorted set) | честное распределение, дороже по памяти |
| **Token Bucket** | бакет пополняется токенами непрерывно | разрешает легитимные всплески, держит средний темп — алгоритм Stripe/GitHub/AWS |

## API

| Метод | Путь | Описание |
|---|---|---|
| GET | `/` | Лендинг + плейграунд + дашборд |
| GET | `/fixed` `/sliding` `/token` | лимитируемые endpoint'ы (принимают `?limit=&window=` для экспериментов) |
| GET | `/status` | статус storage-бэкенда (Redis / in-memory) |
| GET | `/api/stats` | агрегированная аналитика использования |

## Нагрузочный тест

```bash
node tests/load.test.js

ENDPOINT=/token REQUESTS=50 CONCURRENCY=10 node tests/load.test.js
```

## Структура проекта

```
server.js                  # Express-приложение, точка входа
src/
  config/store.js          # Redis / in-memory storage abstraction
  limiters/                # fixedWindow, slidingWindow, tokenBucket
  middleware/clientId.js    # идентификация клиента по IP
  routes/api.js             # HTTP-роуты
  store/stats.js            # in-memory аналитика для дашборда
public/                    # лендинг, плейграунд, дашборд (vanilla JS)
tests/load.test.js         # простой нагрузочный тест
```

## Куда развивать дальше

- Персистентный дашборд (сейчас метрики теряются при рестарте процесса)

- Реальная аутентификация вместо идентификации по IP, если понадобится
- SDK-обёртки (Node, Python) поверх заголовков `X-RateLimit-*`
